## Overview

A fraud detection model trained on the IEEE-CIS dataset, with a dashboard that
scores individual transactions and shows the features behind each score. Built
as a class project. The modeling drew on course resources. The deployment,
the interface, and the explainability layer were my work.

## Approach

I compared four models on held-out ROC-AUC: logistic regression, random forest,
XGBoost, and Gaussian naive Bayes. Tuned logistic regression performed best at
80.9%. I had expected one of the tree-based models to win.

## Results

ROC-AUC is 80.89%. Recall on the fraud class is 67.92%. Precision is 6.91%.

The model catches roughly 68% of fraudulent transactions, covering 63.4% of
total fraud value in the test set, or $5,763.84 of $9,090.46. It flags 485
legitimate transactions to do it, so about 19 of every 20 alerts are false.

F1 comes out at 12.54%, the predictable result of averaging solid recall
against weak precision. I stopped reporting F1 after this project.

Fraud is rare, so a model tuned to catch most of it will always pull in a large
volume of normal transactions, and moving the threshold only trades one type of
error for the other. The right setting depends on what a false alarm costs in
review time, declined cards, and abandoned purchases, none of which appears
anywhere in the dataset. That is a business decision, not a modeling one.

Train AUC of 81.07% against test AUC of 81.51% gives a gap of negative 0.43
points, so the model is not overfitting.

## Explainability

The IEEE-CIS features are anonymized. Columns arrive named V70, C12, and M6
with no published definitions, which makes the model a black box by default. A
fraud score nobody can question is not worth acting on, regardless of its AUC.

I added SHAP so each score decomposes into the features that produced it,
starting from a base rate of 46.78%. V70 and V69, which are Vesta's own
card-activity and device-fingerprint scores, carry the most weight, followed by
card6 (debit versus credit) and C12 (transaction count from the same device).

I also wrote a plain-language glossary for each feature. A chart labeled V292
communicates nothing on its own. Making the output readable took longer than
training the model.

## What I learned

- ROC-AUC of 81% and precision of 7% describe the same model. A single metric
  was never going to be enough to judge it.
- Accuracy is meaningless when the positive class is this rare. The useful
  question is what each type of error costs.
- Explainability is not a bonus feature. If a score cannot be interrogated, it
  should not be acted on.
- Serving predictions required building the feature vector on demand, from
  inputs shaped differently than the training data. That was the bulk of the
  deployment work.

## Status

Complete as a class project. The AWS inference endpoint has been retired, so
the scoring panel no longer returns live predictions. Every metric in the
dashboard is a real result from the trained model.
