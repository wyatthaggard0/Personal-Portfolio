## What it is

A fraud model trained on the IEEE-CIS dataset, with a dashboard that scores a
transaction and shows what drove the score. Class project. The modeling used
course resources. I built the deployment, the interface, and the SHAP layer.

I compared four models on held-out ROC-AUC: logistic regression, random forest,
XGBoost, and Gaussian naive Bayes. Tuned logistic regression came out ahead at
80.9%. I expected one of the tree models to win.

## The numbers

ROC-AUC is 80.89%. Precision on the fraud class is 6.91%. Recall is 67.92%.

The last two matter more than the first. The model catches about 68% of
fraudulent transactions, worth 63.4% of the fraud value in the test set —
$5,763.84 of $9,090.46. To get that it flagged 485 legitimate transactions.
So about 19 in 20 flags are wrong.

F1 lands at 12.54%, which is what you get averaging decent recall with bad
precision. I stopped quoting F1 after this.

Fraud is rare, so anything tuned to catch most of it pulls in a lot of normal
transactions. Moving the threshold trades one error for the other. Where you
set it depends on what a false alarm actually costs — review time, a declined
card, a customer who gives up — and none of that is in the dataset. That part
is a business call.

Train AUC is 81.07% against test AUC of 81.51%. The gap is -0.43 points, so
it isn't overfitting.

## Explaining the score

The IEEE-CIS features are anonymized. The dataset ships columns called V70,
C12, and M6 with no published definitions, so the model is a black box by
default.

I added SHAP so each score breaks into the features that produced it, starting
from a 46.78% base rate. V70 and V69 carry the most weight — those are Vesta's
own card-activity and device-fingerprint scores — then card6 (debit vs credit)
and C12 (transactions from the same device).

I also wrote a plain-language glossary for the features. A chart labeled V292
tells a reader nothing. The glossary took longer than training the model.

## What I'd take from it

- ROC-AUC of 81% and precision of 7% describe the same model. One number
  isn't enough to judge it.
- Accuracy is useless when the positive class is this rare. The useful
  question is what each kind of mistake costs.
- A score nobody can question isn't much use, whatever its AUC.
- Serving predictions meant building the feature vector on demand, from inputs
  shaped differently than the training data. That was most of the deployment
  work.

## Where it stands

Finished as a class project. The AWS endpoint is retired, so the scoring panel
no longer returns live predictions. Every metric in the dashboard is a real
result from the trained model.
